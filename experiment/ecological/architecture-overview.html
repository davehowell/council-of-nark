Council of Nark / Experiment documentation

Ecological review experiment

The experiment gives a model bounded ways to inspect a real pre-fix codebase while keeping Git history, the eventual fix, evidence keys and the controller repository out of model reach.

01Overview

A trusted Go controller starts an isolated Pi process. Pi can send model requests, but it cannot open the source tree. The model asks for source through four custom tools. A separate Go mediator checks each request and returns bounded text.

Scroll diagrams horizontally to see the full width.

What “trusted” means here: the Go controller and mediator are part of the experiment machinery and can read controller-owned files. The respondent model cannot. The seal detects later file changes; it does not prove that the trusted code itself was correct, so that code and its probes remain reviewable inputs.

02Sandboxing and data boundaries

There are two different Seatbelt sandboxes. The network-enabled Pi child cannot read the source. The source-enabled focused-test process cannot use the network. This split avoids giving the model-controlled process both source access and unrestricted transport.

03One review stage

The same stage runner is used for a reviewer or a later fuser. A whole-block controller still needs to assemble continuing-session and multi-review histories for the proposed comparison.

04Proposed five-arm comparison

These arms are the next experiment, not completed results. All use the same source capability, schema, final-length cap and pinned provider/model. The planned Gortex block has 17 review or fuser stages; tool use can create more than 17 provider requests.

S · Single

One omnibus functional review. Proposed cap: 8,000 charged input/output tokens.

I · Informed self-review

Initial review, two revisions and consolidation in one continuing session.

R · Repeated sampling

Three independent omnibus reviews, then one neutral fuser.

F · Functional council

Correctness, architecture and operational-risk reviews, then the fuser.

P · Persona package

The same three functional kernels with K-2SO, GLaDOS and Holly wording.

The proposal gives I, R, F and P up to 32,000 charged tokens each, allocated as 8,000 per stage. Together with S, one block therefore has a proposed ceiling of 136,000 charged tokens. This is a ceiling, not an expected bill.

05Blind human and automated rating

Every output is rated as a code-review and research report. The merged upstream change is shown to every rater as a demonstrated reference resolution, not a gold standard. Supported alternatives, idiomatic trade-offs and findings beyond that patch remain eligible.

06Records, checks and current decisions

A completed attempt is a directory with a manifest that records the path, byte count and SHA-256 digest of every other retained file. Verification recomputes all three and rejects missing, extra or changed files.

Limits of the boundary

  • Seatbelt controls local processes. It cannot inspect provider-side model code, hidden retrieval, caching, moderation or personalization.
  • The provider needs network access for inference. The experiment disables model web tools but cannot prove that a remote service has no undeclared retrieval.
  • A response that crosses a token cap has already been generated. The controller records that unavoidable last-response overrun and stops before another request.
  • The deterministic mock proves lifecycle handling, not review quality or isolation against a malicious kernel/provider.
